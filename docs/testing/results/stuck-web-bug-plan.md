## One causal, fixable bug

`test/real-pc/settle.js:9-15` considers a row working only when its state is `streaming` or its AI page is `building`. A checklist row with `data-state="live"` is therefore declared settled after six seconds of quiet text, even though the web job is still running. The live checklist is the only new row in each affected wait, so this is sufficient to reproduce the early close.

The red regression check was run against the current checkout:

```text
node -e "const s=require('./test/real-pc/settle'); const i=[{state:'live',pageState:null}]; if(!s.stillWorking(i)) throw Error('RED: live checklist is treated as settled'); if(s.settled({n:1,before:0,items:i,quietFor:6000,quietMs:6000})) throw Error('RED: live checklist passes settled predicate')"
```

It fails at the first assertion with `RED: live checklist is treated as settled`. The smallest repair is to make a live checklist item working (and add this regression to the focused real-PC helper tests); then rerun the affected journeys. No repair was made in this read-only pass.

The c4 J05 paired log records `waitReply` at 14.1 seconds with only `Looking on the web`, `endState:false`, followed by the driver closing the app; its app log has `browser.ensure` and then `job.waiting` with `kind:app_quit`, but no `web.no_window`, `SEARCH_BUSY` or `job.stuck.*`. The screenshot is [J05 01-news](https://github.com/vikas53953/foo-agent/blob/822a7a5d452c9292de814116eb12c6c4e51aebbd/real-ai/c4d4187-claude/s0/2026-10-23T02-12-16-521Z-J05-web/01-news.png), and the paired log is [J05 log](https://github.com/vikas53953/foo-agent/blob/822a7a5d452c9292de814116eb12c6c4e51aebbd/real-ai/c4d4187-claude/s0/2026-10-23T02-12-16-521Z-J05-web/log.jsonl).

B14 reproduces the same sequence on the second, news request: the first post-relaunch answer settles, `chat.turn_recovered` is logged, then the news `waitReply` returns after 11.4 seconds with a live checklist and `endState:false`; the driver closes, producing `job.waiting(app_quit)`. See [B14 screenshot](https://github.com/vikas53953/foo-agent/blob/822a7a5d452c9292de814116eb12c6c4e51aebbd/real-ai/c4d4187-claude/s3/2026-10-23T02-15-08-348Z-B14-restart-mid-reply/02-news-after-reopen.png) and [B14 log](https://github.com/vikas53953/foo-agent/blob/822a7a5d452c9292de814116eb12c6c4e51aebbd/real-ai/c4d4187-claude/s3/2026-10-23T02-15-08-348Z-B14-restart-mid-reply/log.jsonl). This is a driver cancellation of an in-flight browser read, not proof of a provider outage or a browser-renderer failure.

## Provider and placeholder checks

The c4 AI-turn receipts show `claude-cli` turns with `outcome:ok`; no provider-unavailable condition is evidenced. The keyless web-window wiring fix is already present in this tested commit (`EngineWebOptions.page`, `jobWindowPages`, and `test/integration/browser/webPages.test.ts`), and these c4 logs contain neither `web.no_window` nor `SEARCH_BUSY`. The earlier no-window cause from the pre-wiring run should not be reassigned to c4.

The repeated `PROMPT_PLACEHOLDER_EMPTY` lines are not proof that search results were substituted into an empty slot. `Engine.stepProtocol()` and the intake adapter pass empty `vibeLine` and `emoji` values (`src/engine/Engine.ts:633-634,712-713`); `fillPlaceholders` logs empty strings by design (`src/engine/prompt/PromptBuilder.ts:186-201`). They occur once per identity build and are orthogonal to the live checklist wait.
