## T8 · Reply time uses the test clock after the engine starts (blocked by: none) — bug from foo-verify (PR #6)

Bug: in an e2e run the user's message shows 9:41 AM but foo's reply shows 9:00 AM. Cause (triaged by the M4 lead):
the engine's FakeClock starts at `TEST_EPOCH_MS` (03:30 UTC = 9:00 IST, `src/engine/index.ts:21`) and only follows
main's clock through `test.clock` messages, sent from `test:clock` (`src/main/test/testHooks.ts:88`) via
`engine.send`, which is a no-op while the engine is not yet live. A test that sets the clock before the engine connects
(it forks at ready + 300 ms), or any engine restart, leaves the engine at 9:00 while main is at 9:41. Fix: when the
engine (re)starts in a FOO_TEST run, main sends `test.clock { now }` with its clock in `supervisor.onStarted`
(`src/main/index.ts:86`), before `settings.changed`. Move the onStarted body into a small tested function (e.g.
`src/main/engine-supervisor/hello.ts`) so a unit test can prove the order and the clock value.

- Test first: unit test (main clock set to 9:41, engine not live, then started → first message is `test.clock` with
  9:41) and a check in `test/e2e/m3-replies.spec.ts` that foo's reply time equals the user message time after a
  `test:clock` set before the first send.
- Owns: `src/main/engine-supervisor/hello.ts`, the `onStarted` lines of `src/main/index.ts`, `test/unit/m4-engine-hello.test.ts`.
- Branch `claude/foo-m4-t8`, draft PR into `claude/foo-m4-fgejhm`.
